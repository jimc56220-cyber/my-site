# JWT的思考

### JWT解决了什么问题？

就是传统的用户认证大家都是用session在你登录的时候把你的用户信息储存在session里面然后每次请求都去重新认证你的session这样会占用内存跟存储所以说大家后来就用JWTJWT在我看来它的核心就是只验证不储存 也就是所谓的 无状态认证 。

### 那具体是怎么实现的呢？

首先你登录的时候服务器会验证你的账号密码验证通过之后它会给你发放一个token。

这个token有三块部分组成一个是header一个是payload一个是signature，header里面是你的算法名称，然后payload里面是你的基础信息比如你的user ID，你的过期时间。然后签名是怎么来的？签名就是把你的header跟payload先转码成Base64URL编码然后用算法就是你header里面的算法，和服务器自己的密钥计算一遍，计算成你的签名，每次你的请求就会携带这段token后台接到服务器之后会根据你的header跟payload重新计算你的签名，如果是对的并且没过期，那它就放行，反之就请求失败。



### 但这样也有一定的局限性。

比如说用户修改密码，用户；账号被封或者用户主动退出后，他的旧token依旧可以用，或者说当你的token被盗的时候，攻击者也可以直接攻击，你完全就没有办法。这就是无状态这个设计的弊端，所以现在很多企业会用JWT加Redis的思路JWT负责认证Redis负责控制。简单来说就是你的payload里面不是会有你的user ID吗然后他就会把你的user ID传到Redis里面，然后每次他就会计算出来之后会查一下在Redis里面有没有的user ID，如果是有的话那就跟之前一样，如果没有的话就拒绝访问。



### 那这样有什么好处呢？



好处就在于你可以控制这个token在用户退出之后你就可以直接删除Redis里面的user ID以达到删除这个token的目的，或者说呃在封号之后啊，在被盗之后啊，你可以让他立刻失效。



### 我的思考

如果说你现在又开始存储那么当时那么不用session的意义？session过占存储更多，而这一套只需要把信息就是把你的user ID储存在Redis里面。这样的话即使虽然说依旧是储存，但是更可控而且好你的内存跟储存更少。

# HashMap的思考

### 第一hash map的数据底层结构是什么？

​      他的数据底层结构是数组，链表跟树。简单来说它的具体过程， 就是先计算你的hash值 ，计算完的值作为你的index ，然后当然一开始这些index就是排好的123456 ，所以说它就是数组结构 的。那为什么说还有链表结构呢？因为会出现hash冲突有不同的数据算出来的hash值会是一样的，那么他们就会以链表的形式在同一个index，后储存当hash冲突的数据过多时，他们就会以树的结构存在以方便查询。



### 为什么数组长度必须是二的幂？

这是有三个原因

第一个原因是被我让index计算的更快hash map下面下标的计算可以转化为二进制来进行位运算，这样的话计算效率会快很多。

再有一个就是扩容的时候相当一部分hash code不会改变。

还有一个就是让它的分布更均匀，但这个我不是很理解。
